# AGENTS.md

Guidance for coding agents working in this repo. Read `README.md` for the game itself and `ROADMAP.md` for planned chambers and engine work.

## What this is

**Shiftbound** (repo: XanderPuzzle): a browser-based first-person gravity-puzzle game in TypeScript on Babylon.js 7, bundled with Vite. Levers rotate gravity onto one of six axis-aligned directions (`'+X' | '-X' | '+Y' | '-Y' | '+Z' | '-Z'`). There is no backend; the build is a static bundle deployed to GitHub Pages.

## Commands

```bash
npm install
npm run dev       # Vite dev server on :5173 (host: true)
npm run build     # tsc -b && vite build -> dist/
npm test          # node --experimental-strip-types --test tests/*.test.ts (Node 22.6+)
npm run typecheck # tsc -b (src) and tsc -p tsconfig.tests.json (tests/, e2e/)
npm run lint      # ESLint (eslint.config.js)
npm run format    # Prettier --write (.prettierrc.json); format:check is the read-only check
npm run test:e2e  # Playwright chamber smoke tests (needs `npx playwright install chromium` once)
```

Before you call a change done, run `npm run typecheck`, `npm test`, `npm run lint` and `npm run format:check`. CI (`.github/workflows/test.yml`) runs them on every PR and push to `main`, and the job name `Unit tests` is a required status check, so don't rename it. `lint.yml` (job `Lint and format`) runs the last two. `build.yml` deploys `dist/` to Pages on push to `main`.

ESLint (typescript-eslint recommended, with `eslint-config-prettier` turning off style rules) and Prettier are set up; run `npm run format` rather than hand-formatting. Prettier sets the style: 2-space indent, single quotes, semicolons, lines up to 120 characters. Keep `strict` TypeScript.

## Layout

- `src/babylonSideEffects.ts`: side-effect imports (collisions, picking, edges, glow, shadows, particles, engine extensions) that deep Babylon imports no longer pull in. `main.ts` imports it first.
- `src/main.ts`: the entry point, about twenty lines: it awaits `createApp()`, applies the settings, wires the menus and the page's events, and starts the frame loop. Everything else is in `src/app/`. Progress lives in `src/progress.ts` (`shiftbound.progress`, keyed by each chamber's stable `id` in `CHAMBERS`, with best times and fewest shifts; never change or reuse an id). `?unlockall` must never write progress. `localStorage` keys are prefixed `shiftbound.`.
- `src/title/`: the title's outside view. `TitleView.ts` owns its camera (`camera`, shown in place of the player's while the title shot holds) and sets the backdrop options for it (anchored on the chamber, with the Crown and planet in one frame); `titleShot.ts` is the Babylon-free maths of where the camera and star stand round the chamber's hull, tested by Node (`tests/titleShot.test.ts`).
- `src/game/GameState.ts`: the game-flow state machine (`title`, `playing`, `falling`, `descending`, `paused`, `chamberSelect`, `won`, `ended`; `descending` and `ended` are the final fall out of an `ending` chamber and the end card): a pure `transition(state, event)` table, derived queries (`simulates`, `isFrozen`, `viewOf`, ...) and the `GameState` holder. Babylon-free and tested by Node (`tests/gameState.test.ts`). To add a state, add its kind and transition rows and its answers to the queries there, extend the tests, and add an `onChange` branch in `src/app/menus.ts` (`wireMenus`) only if it has a visible effect.
- `src/game/stuck.ts`: Babylon-free `reachableAxes` and `leversExhausted`, the lever-only check that the exit's gravity can still be reached. `checkTrim` in `src/app/shifts.ts` logs `NO_TRIM` once when it turns true. Tested by Node (`tests/stuck.test.ts`, plus The Lockout case in `tests/chambers.test.ts`).
- `src/game/undo.ts`: Babylon-free `UndoStack<T>` (capped at `UNDO_LIMIT`), the stack of chamber snapshots behind Z. `stepChamber` (`src/app/chamberStep.ts`) saves a `ChamberSnapshot` just before each hand-thrown lever fires (via `GravitySwitch.canFire`) and restores it on undo; `LevelDynamics.snapshot/restore`, `GravitySequencer.snapshot/restore`, `GravitySwitch.revive` and `PlayerController.getLook` are the parts it needs. Tested by Node (`tests/undo.test.ts`).
- `src/gravity/GravitySystem.ts`: the single current gravity axis and its change listeners.
- `src/input/`: `InputSource.ts` is the Babylon-free input interface (`InputFrame`, `mergeFrames`, `stickVector`, deadzone/look-curve maths) and `InputManager.ts` reads and merges the sources once per frame and tracks the last-used device (`lastDevice`, which drives HUD wording); both are tested by Node like `boxPhysics.ts` (import with explicit `.ts` extensions and no constructor parameter properties). `KeyboardMouseInput.ts`, `TouchInput.ts` and `GamepadInput.ts` implement `InputSource`; `runFrame` (`src/app/frame.ts`) reads the manager once per frame and passes the frame to `PlayerController.update`.
- `src/player/PlayerController.ts`: merges the input sources' frames and drives a kinematic body oriented by a smoothly interpolated "up" vector.
- `src/player/jumpAssist.ts`: Babylon-free coyote time and jump buffering (`JumpAssist`), tested by Node.
- `src/level/Builder.ts`: the API chambers are written against (`box`, `slab`, `tube`, `grate`, `glass`, `barrier`, `addSwitch` (with `{ once }`), `addRelativeSwitch`, `addSequenceSwitch`, `addSpentLever` (a burnt-out lever, set dressing only), `addCrate` (with `{ stamp }`), `addFixedCrate` (a crate-looking solid outside the crate physics), `modelCube` (a small lit or dark cube for the Orrery's model of the field), `addPlate` (crates only or crates and player; `inverted` for one that must stay clear), `addDoor`, `placard`, `note`, `finish`), plus `V()` and the wall thickness `T`. `finish()` also stands the attendant printer (`BuiltLevel.printer`: bed, posts, gantry; set dressing that collides with nothing) around the spawn point, and the same bay lit amber at the exit (`BuiltLevel.reclaimer`, where the attendant is taken apart to be reprinted at the next cube; none in an `ending` chamber), and takes `vista: true` for a chamber with a window (see the conventions below).
- `src/level/spec.ts`, `buildSpec.ts`, `specs/`: a simple chamber (slabs, boxes, tubes, glass, fixed levers, placards, no crates, doors or timers) can be plain data. `spec.ts` is the Babylon-free `ChamberSpec` type and `checkSpec` (axes, normals, empty boxes, lever route), `buildSpec.ts` is the one builder that reads a spec (`buildFromSpec`), and `specs/<name>.ts` holds the data; the chamber file is a three-line wrapper. Specs import with explicit `.ts` extensions. `tests/chamberSpec.test.ts` runs `checkSpec` on each; add a row when you convert a chamber. Converted so far: every chamber without crates, doors, plates, relative or sequence levers or a timer (Vault, Shaft, Divide, Spiral, Chimney, Staircase, Descent); the others still need the spec extended first.
- `src/level/specCodec.ts`: Babylon-free `encodeSpec`/`decodeSpec`, a `ChamberSpec` as a URL-safe string (`v1.<base64url of deflate-raw of positional JSON>`), for shared chambers. Decoding takes a stranger's input: it validates every field, caps the link, the inflated size and the chamber's size (`LIMITS`), and runs `checkSpec`. A page opened with `#c=...` (`sharedSpec` in `src/app/flags.ts`) shows that chamber as a guest in the ordinary game: `app.guest` holds its factory and `levelIndex` is `GUEST_INDEX` (-1), so restarts, skin swaps and the win (which starts it over) all build the guest, while the loader and the chamber list are the real catalog. While it shows, `sandbox` is true (no progress, hints or serials) and `shared` is true; picking a chamber from the list clears `app.guest` and calls `leaveShared()` in `pickLevel`, and the page is then ordinary. `sandbox`, `shared` and `progressWritable()` are read when needed, never copied. A `hashchange` to a `#c=` fragment reloads the page (a link pasted into an open tab changes only the fragment), and `leaveShared` clears the fragment. `src/app/sharedChamber.ts` decodes the link; a bad one is logged and the page is ordinary from the start. `npm run share -- <id | file.json>` prints a link. A format change needs a new `SPEC_VERSION` and the old decoder kept, since links in the wild keep working. Tested by `tests/specCodec.test.ts` and the two `#c=` rows in `e2e/chambers.spec.ts`.
- `src/level/Placard.ts`, `placardText.ts`, `fonts.ts`: text painted on chamber faces and crates (see NARRATIVE.md). `placardText.ts` is the Babylon-free size, orientation and handwriting maths, tested by Node; `Placard.ts` draws it on a canvas texture on a thin plane; `fonts.ts` loads the two bundled fonts in `public/fonts/` (SIL Open Font License, licences alongside). Each skin's `placardInk` sets how stencils are painted; the Margin's notes look the same in every skin.
- `src/gravity/axes.ts`: Babylon-free axis maths and the `GravitySequencer`; tested directly by Node like `boxPhysics.ts`.
- `src/app/`: the running game. `App.ts` defines `App`, the one object that holds every long-lived service (engine, scene, input, HUD, sound, `game`, ...) and every piece of state more than one module needs (`level`, `levelIndex`, `skin`, `settings`, `progress`, `shifts`, `levelTime`, ...), plus small helpers over it (`beep`, `cubeOf`, `nextIndex`, `reducedMotionActive`, `persistProgress`). The other files are functions that take `app`: `bootstrap.ts` (`createApp`: builds it all, awaiting the first chamber's code), `chamberFlow.ts` (`startLevel`, `restartLevel`, `advance`, `pickLevel`, `whenLoaded`, `setSkin`, `syncPrinter`, `beginDescent`), `chamberStep.ts` (`stepChamber`: one simulated frame of the player, levers, cycle, crates, falling and the win), `shifts.ts` (`undoLastShift`, `checkTrim`), `menus.ts` (pause and chamber-select actions and `wireMenus`, which sets the one `game.onChange` handler where every overlay is shown and hidden), `bindings.ts` (`bindEvents`: HUD buttons, pointer lock, keys outside play, resize, the service worker), `applySettings.ts`, `frame.ts` (`runFrame`: menu input, the step, the sky, the draw) and `debugHook.ts` (`window.__debug`). Rules for `App`: add a field only if two or more modules use it; state one module owns stays in that module or in a class of its own held on `App` (`Sky`, `HintLadder`, `CratePreview`, `ChamberSelect`); no game-flow flags (flow is `GameState`: send it events and react in `onChange`); `app.level` and `app.skin` are rebuilt by `startLevel` and `setSkin`, so read them from `app` each time and never keep a reference. Imports run one way: `App.ts` imports none of the others, `chamberFlow.ts` only `App.ts`, and `bootstrap.ts`, `frame.ts`, `bindings.ts` and `debugHook.ts` sit on top. Chamber code is lazy: `startLevel(app, index)` needs the chamber's module already loaded, so anything that starts a chamber the player may not have fetched goes through `whenLoaded(app, index, then)`; a restart or skin change of the current chamber never waits. `flags.ts` is the URL flags and the storage probe (`sandbox`, `unlockAll`, `playtesting`, `store`), read once at load. `Sky.ts` is everything outside the chamber once a frame: which camera is in use (the title's or the player's), where the planet lies, the backdrop's frame, and whether a storm just broke; `frame.ts` decides when the title's outside view is up (the title, with the player still on the print bed) and passes that in. `ChamberSelect.ts` keeps the chamber list (highlighted row, unlock rule, row text) and preloads the highlighted chamber's code.
- `src/level/chambers/`: one file per chamber, each default-exporting its factory (and still exporting `build<Name>` by name). `catalog.ts` is the Babylon-free list `CHAMBERS` (the play order: `id`, `cube`, the `name` shown in the chamber select, `par`, the fewest gravity shifts that clear a non-timed chamber, and `load`, a literal dynamic `import()` of the chamber's file) and `SANDBOX`. Nothing imports a chamber file statically, so each is its own chunk of the build, fetched when first needed and precached by the service worker like every other output file. `ChamberLoader.ts` (Babylon-free, tested by Node) fetches and remembers the factories: `get` is synchronous for a chamber already loaded, `load` returns a promise, `preload` fetches in the background. `index.ts` re-exports all three. Tests that build chambers load every module first (`(await c.load()).default`).
- `src/level/Dynamics.ts`: crates, pressure plates, doors and their per-frame update. A crate more than `CRATE_LOST_MARGIN` outside the level bounds has fallen out through a hole and is `lost` until the chamber restarts. `predict` runs the crates' sub-stepping on copies to find where they would rest under a gravity vector (an approximation: doors keep their current state), and `showPreview` draws the ghost outlines shown in reach of a lever (paced by `src/level/CratePreview.ts`). Tested headlessly by `tests/dynamics.test.ts`.
- `src/level/GravitySwitch.ts`: the lever interactable.
- `src/physics/boxPhysics.ts`: swept AABB physics for crates. It must stay free of Babylon imports so Node can test it directly.
- `src/environment/`: what lies outside a chamber. `fall.ts` is the Babylon-free escape/fall maths (level bounds, `FallTracker`, planet distance, and `stormStrength`, the once-a-minute stellar storm the Crown and the planet's aurora answer), tested by Node like `boxPhysics.ts`; `ballastField.ts` is the Babylon-free layout and motion of the other cubes you fall past (and `chamberHull`, the cube that dresses the outside of the current chamber like them), tested by Node; `SpaceBackdrop.ts` draws the space outside: inside a chamber only a black sky and the planet (so a hole is black, or shows the planet if it is in the floor); after an escape also the stars, field cubes, the Crown (a dark spoked ring overhead), the chamber's hull and speed streaks. `BackdropFrame` options: `vista` shows the stars, field and Crown from inside a chamber with a window; `anchor` and `crownDistance` place everything around the chamber for the title's outside view; `hullDark` dresses the chamber's hull as a dark cube; `arrival` lights one new point on the planet under the camera (the ending).
- `src/skins/Skin.ts`: the skins (`station`, the default: plated metal with a painted band per panel in the face's axis colour; `axis`, `monolith`, `draft`, `neon`): per-axis materials, lighting, sky, post-processing. The `colorAssist` setting swaps the axis colours for `src/skins/axisPalette.ts`. `SKIN_IDS` is the order K cycles through and the stored choice is an index into it, so only append to it; `DEFAULT_SKIN` is what a new player gets. The headless tests build with `axis`.
- `src/ui/HUD.ts`: Babylon GUI overlay. `printIn` is the wipe that opens the view each time the attendant is printed (a plain fade under reduced motion); `printOut` is the same wipe run backwards, played when the attendant is reclaimed at an exit. The wipe's length comes from `src/ui/printTiming.ts` (Babylon-free, tested by Node) and is shorter on a repeat start of the same chamber.
- `src/ui/PauseMenu.ts`: the pause menu (resume, restart, chamber select, fullscreen, update, settings, controls reference); added on top of the HUD's GUI texture. Keep its controls reference in sync with the real bindings.
- `src/narrative.ts`: Babylon-free story text in the facility's voice (the attendant serial and the predecessor's, `PREDECESSOR` and `MARGIN_SIGN`; cube labels; duty, recovery and win log lines, `CROWN_BALANCED`; the Descent's alarms, `DESCENT_OUT_OF_TRIM` and the end card) and the per-chamber story state of the fall view (`darkFraction`, `planetLights`); tested by Node. Each chamber's cube serial is the `cube` field in `CHAMBERS`. The design, voices and writing rules are in `NARRATIVE.md`.
- `src/game/chamberSnapshot.ts`: `takeSnapshot` and `restoreSnapshot`, what undo saves and puts back (player, gravity, crates, plates, doors, levers, sequencer). `src/game/reclaim.ts`: Babylon-free `touchesPlate` and `RECLAIM_HOLD`, the win check on the reclaimer's plate; tested by Node.
- `src/level/CratePreview.ts`: paces `LevelDynamics.predict`/`showPreview` for the lever in reach. `src/ui/prompts.ts`: Babylon-free `PROMPTS`, the wording that names a key or button per input device; keep it in step with the bindings.
- `src/hints.ts`: the hint ladder, Babylon-free: `hintTier` (time in the chamber and restarts of it), `HintLadder` (one chamber visit's place on it) and `hintFor`, and `MORE_HINTS`, each chamber's second and third hint keyed by `id`; tested by Node (`tests/hints.test.ts`). The lines are in NARRATIVE.md's "The ladder".
- `src/random.ts`: Babylon-free seeded random (`random`) and string hash (`hashString`), so layouts and handwriting repeat exactly.
- `src/time.ts`: Babylon-free `simDelta`, the one clamped frame delta (`MAX_SIM_DELTA` = 1/20 s) that `runFrame` feeds every system; tested by Node.
- `src/gravity/shiftSound.ts`: Babylon-free axis -> shift-sound mapping (`shiftTone`); tested by Node.
- `src/audio/`: `sounds.ts` is the Babylon-free list of recorded sounds and the maths behind them (impact volume, the wind of a fall), tested by Node, which also checks every listed file exists; `AudioEngine.ts` plays them with Web Audio: the looping music, the effects, the fall's wind (filtered noise, no file) and the small synthesized `beep`s. It does nothing until `unlock()` runs from a user gesture. The files are in `public/audio/`, all CC0, with sources and processing in `public/audio/CREDITS.md`: add a row there for any new file, and take only CC0 or similarly unrestricted audio.
- `src/skins/axisPalette.ts`: Babylon-free colour-blind palette for the six gravity axes (Okabe-Ito), and `relativeLuminance`; tested by Node (`tests/axisPalette.test.ts`).
- `src/playtest.ts`: Babylon-free playtest log (`?playtest` only): `PlaytestRecorder` records each chamber visit (time, shifts, restarts, falls, undos, stuck notices, hint tier, clear), `parsePlaytestLog`, `playtestFileName` and the `shiftbound.playtest` storage helpers; tested by Node. `src/ui/download.ts` downloads the saved file.
- `src/settings.ts`: Babylon-free settings model (`Settings`, defaults, limits, `parseSettings`/`loadSettings`/`saveSettings`, `stepSetting`), stored as JSON under `shiftbound.settings`; tested by Node. Includes `colorAssist`, the colour-blind palette toggle.
- `src/pwa/`: `cachePolicy.ts` Babylon-free cache naming/strategy tested by Node; `sw.template.js` service worker source that `build/pwaPlugin.ts` fills with the precache list to emit `dist/sw.js`; `register.ts` production-only registration and update flow; `fullscreen.ts` fullscreen/standalone/orientation helpers.
- `e2e/`: Playwright chamber smoke tests (`chambers.spec.ts`), run against the Vite dev server by `playwright.config.ts`.
- `tests/`: `node:test` unit tests. They import source with explicit `.ts` extensions (`../src/physics/boxPhysics.ts`).
- `tests/chambers.test.ts` and `tests/helpers/`: headless chamber invariants. The test builds every entry of `CHAMBERS` under Babylon's `NullEngine` with the real `axis` skin and checks: `CHAMBERS[i].name` matches `finish()`; axes are valid; spawn and exit are inside `bounds`, the spawn sphere is not in a solid and has floor under `entranceAxis`; `exitAxis` is reachable from `entranceAxis` through the levers and every lever can change gravity from a reachable axis; crates do not overlap solids or each other; every door has plates that belong to the level; `dispose()` restores mesh/material/texture/light/observer counts. `helpers/hooks.mjs` (registered by `helpers/headless.ts` before `src` is imported dynamically) resolves extensionless imports and compiles `.ts` with the repo's TypeScript, so no `src` import needs rewriting; `headless.ts` also stubs `OffscreenCanvas` with a no-op canvas so skin textures can be created. - `tests/crateRoutes.test.ts`: replays gravity routes on the real crate physics, headlessly, with the player standing at a given point, and checks the doors and where each crate ends up. Every crate chamber has a row for its route and a row for each wrong order its design relies on (which must fail). Add or update rows when you change a crate chamber.

## Adding or changing a chamber

1. Create `src/level/chambers/<name>.ts` exporting `build<Name>(scene, skin): BuiltLevel`, and end the file with `export default build<Name>;` (the catalog loads the default export). Start by copying a similar chamber; `chimney.ts` is a good, recent example.
2. Construct a `Builder` with an accent `Color3`, lay out geometry with `slab`/`tube`/`box`, place levers with `addSwitch(position, wallNormal, targetAxis)`, and return `b.finish({ name, hint, spawnPosition, entranceAxis, exitAxis, exitCenter, exitRadius })`.
3. Add it to `CHAMBERS` in `chambers/catalog.ts` with a new unique, permanent `id`, the same `name` it passes to `finish()`, `load: () => import('./<name>')` (a literal path, so the bundler can split on it; do not import the chamber statically anywhere) and, unless it is on a timer, a `par` (the shortest lever route's shift count, which `npm test` checks is a lower bound), then update the chamber list in `README.md` and its status in `ROADMAP.md`.
4. Give it its two extra hints in `MORE_HINTS` (`src/hints.ts`), keyed by the same `id`: `tests/chambers.test.ts` fails until it has them. Changing a chamber's route means re-checking both lines against the new route, and the chamber's table in NARRATIVE.md.

Conventions and pitfalls:

- Import Babylon from deep module paths (`@babylonjs/core/Maths/math.vector`, `@babylonjs/core/Meshes/Builders/boxBuilder` for `CreateBox`, `@babylonjs/gui/2D/controls/button`), never from a package root; the roots pull in most of the engine. A feature that fails at runtime with "needs to be imported" (or silently does nothing, like collisions) needs a side-effect import in `src/babylonSideEffects.ts`, with a comment saying why.
- Everything is axis-aligned boxes. Every box face is the floor under exactly one gravity axis (the one pointing into it), and skins colour faces by that axis. Don't add rotated geometry.
- Place a lever so that what it moves is in front of the player when they throw it: on a low glass screen or block facing the crates, not on a wall with the crates behind them. Check where the player lands after the shift: not in a crate's lane (crates treat the player as a solid obstacle), and in reach of the next lever.
- A trap hole belongs where a wrong move puts you (under a decoy lever's new floor, at the end of a fall you failed to steer), and must be visible from where that move is made. Don't put holes in long chambers while there are no checkpoints.
- A chamber is won by standing on the reclaimer's plate, which `finish()` puts on the floor under `exitCenter` along `exitAxis` (`npm test` checks it is there with room to stand). Touching the plate counts under any gravity. Before you trust a design, ask how else the exit or a lever could be reached: walking up a wall, a doorway that becomes a hole in the floor, steering into an opening mid-fall, throwing a lever in passing.
- Use surface roles deliberately: `b.wall`/`b.floor` (shell), `b.alcove` for corridors, `b.exit` for the exit path and anything the player must find, and the default `feature` for interior obstacles.
- Holes cut with `slab(..., hole)` run to the slab's edge, which can leave a floor gap under a doorway. Fill it with a sill `box` (see the existing chambers).
- A skylight is a `slab` hole filled with `b.glass` (glass is as solid as wall, for the player and for crates), plus `vista: true` in `finish()`. Without `vista`, a hole or a window shows only black sky and the planet. Remember the win check and trap-hole pitfalls still apply to anything you open.
- Describe the gravity route in the file's doc comment (e.g. `-Y -> +Z`) and keep it in sync with `entranceAxis`/`exitAxis`.
- Use `?sandbox` in the dev URL for the crate/plate/door test room, and `?skin=<id>` to force a skin (`station`, `axis`, `monolith`, `draft`, `neon`).
- Placards and notes: `b.placard(at, normal, readAs, text)` puts text on the face with outward `normal` at point `at`, upright under gravity `readAs`; on a face that is the floor or ceiling under `readAs`, pass `{ top }`. Lines break only at `\n`. `npm test` checks every placard sits on a real, uncovered face, and that each chamber stencils its `CUBE` serial from `CHAMBERS`. Keep the text in the voices and rules of NARRATIVE.md, and keep its chamber script in sync.
- Every mesh, material and listener a level creates must be released in `dispose()`. Go through `Builder` so `finish()` handles this; skin sub-materials outlive levels and must not be disposed with them.

## Verifying gameplay

`npm run test:e2e` (CI job `Chamber smoke tests`, `.github/workflows/e2e.yml`) loads every chamber and replays its gravity route by teleporting to each lever via `window.__debug`. When you add a chamber, add a row to `ROWS` in `e2e/chambers.spec.ts` (same order as `CHAMBERS`): the lever indexes (order of the `addSwitch` calls, see `__debug.switches()`) and the gravity expected after each throw. When you reorder or add levers or change a chamber's route, update its row; keep the suite passing. A timed chamber's row is `timed: true` with `axes` listing the first few automatic shifts. It does not walk the player, so it still does not replace a manual playtest. The suite runs in the `title` state (a keyboard player can move there); `__debug.begin()` leaves the title as a tap would, for scripts that need the `playing` state or the inside view at the spawn. `__debug.audio()` reports the audio engine's state. The suite waits in game time, not wall-clock time (`__debug.simTime()`, with `simWait` and `untilSim` in the spec), because the game clock is clamped per frame and runs slow under CI's software WebGL; write new waits the same way, and never with `waitForTimeout` or a wall-clock `expect.poll` on something the simulation has to reach. It also renders at reduced resolution (`__debug.setRenderScale`) and in the Axis skin to keep the frame rate up. `__debug.storm()` starts a stellar storm at once.

Typecheck and unit tests do not tell you whether a chamber can be completed. When you change geometry, lever placement, or player movement constants (jump height, air control, lever reach), say plainly that the change still needs a manual playtest, and say what to check: can each lever be reached from the surface the previous shift leaves you on, and can the exit be reached. Don't claim a chamber works because it builds.

## Git

- Work on a branch and open a PR into `main`. Commit only when asked.
- Commit subjects are short, imperative and sentence case, with no prefix (e.g. `Add chamber V, The Chimney; fill the floor gap under doorways`).
